# Architecture reference

Read the relevant section when changing adapter wiring, metadata identity, replication, playback transport, or desktop startup. Domain terminology is defined in [CONTEXT.md](../CONTEXT.md).


Go modular monolith — single binary, React SPA embedded at build time (`-tags prod` via `internal/api/embed.go`; `--dev` proxies Vite). Both entry points (`cmd/reverb` server and `desktop/` Wails) share one composition root in `internal/app/build.go` (`Build` wires, `StartBackground` starts) so dependencies are wired once; entry points only own how they listen/shut down. Hot-reload of adapters happens live via `internal/app/reload.go` (`ServiceReloader`) with no restart.

### Adapter/seam pattern (the core design)

Three pluggable seams, same shape: interface + adapters + conformance suite + explicit registry, **no `init()` side-effects**.

- **`library`** — `internal/library/library.go` (`LibraryAdapter`); adapters `internal/library/subsonic` + `internal/library/embedded` (built-in vs external, see below) and `internal/library/localfiles` (a plain folder, for the phone profile); `conformance.go` (`RunConformanceWith` takes the ids of an adapter whose ids come from its data). The backend serves library records; Reverb persists catalog identity, bindings, metadata overrides, and materialized sync state in SQLite.
- **`search`** — `internal/search/search.go` (`SearchSource`); adapters `internal/search/deezer` (keyless), `internal/search/spotify`; `aggregator.go` fans out to all enabled sources concurrently over SSE with per-source `Envelope{Status,Results,Error}`; `conformance.go`. Optional caps via type assertion: `DiscographyProvider`, `TrackProvider`, `PlaylistProvider`, `PlaylistSearchProvider`, `SimilarArtistsProvider`.
- **`downloader`** — `internal/download/download.go` (`Downloader` + `DownloaderEntry{Order}` for per-instance granularity); adapters `internal/download/spotdl`, `internal/download/lidarr`, `internal/download/ytdlp`, with spotDL and yt-dlp also available as in-process variants (`NewInProcess`) that run the Python module through `internal/pyrun` and always keep the source's stream; `conformance.go`; `download/manager.go` owns queue/workers/dedup-join/fallback/scan-debounce/cancel/retry. Optional caps via type assertion: `AsyncDownloader` (Submit/Poll, reconciler lane) and `ChapterLister`.

Registration: `internal/registry/registry.go` holds constructors by name; `internal/app/build.go` registers `subsonic` / `spotify`+`deezer` / `spotdl`+`lidarr`+`ytdlp` explicitly, plus `registry.RegisterCapability("async", ...)`. `internal/wiring/wiring.go` (`Builder`) builds the active `ServiceBundle` from enabled `adapter_instance` DB rows; `internal/app/reload.go` rebuilds it on HTTP adapter mutations (`internal/api` adapter handlers) and publishes one atomic snapshot of request services, matcher, and track lookup so HTTP, `resolver`, and `extstream` read the active configuration. The application runtime serializes reload with shutdown, starts the candidate manager, publishes it, stops the old manager, and redispatches its requeued jobs. A build failure leaves the active snapshot intact. HTTP only requests reload and reads `Current()`; it owns no worker lifecycle. Requests that already captured an old service may finish while its workers retire.

Library modes (`internal/library/embedded`): **built-in** bundles Navidrome as a supervised child process against the same music dir (waveform-peaks via local file access); **external** points at a user-provided Subsonic/Navidrome. Mode is boot-bound (restart to change).

Profiles (`app.Options.Profile`, ADR 0003): the zero value is the desktop and server. **`ProfilePhone`** builds a reduced Device from the same root: the library is `localfiles` over `<dataDir>/music` (`wiring.Builder.SetLocalLibrary`), which P2P file sync fills; there is no Navidrome supervisor and no seeded adapter rows; yt-dlp and spotDL are registered as their in-process variants over `Options.Python` (a `pyrun.Runner`: the platform's embedded interpreter, or host Python from `REVERB_PYTHON` on Linux), default downloaders write into the folder, and external streaming resolves through the same runner; the download manager is built even with no downloader, since managed playlists hang off it; portable-name migration and library-playlist migration are left out, and `/library/status` reports mode `local`, which keeps uploads and library deletion on the desktop. `internal/library/localfiles` derives ids from the data (track from its path, album from artist and title, artist from name) so a rescan and a peer's file at the same path keep them; it reads tags with a pure-Go reader, serves bytes with single byte-range support, never decodes audio (no duration), and refuses to write playlists, since a playlist file in the folder would replicate to every peer as music.

### Composition & control flow

- `internal/app/build.go` — composes `auth`, `catalog`, `resolver`, `download.Manager`, `playlistsync`, `scrobble`, `extstream`, `api.Deps`, `sync`, `p2p`; entry points call `Build` then `StartBackground` (supervisor, manager, backfill, sync scheduler, scrobble worker, p2p host + sync/file handlers).
- `internal/core` — domain types (`Artist`/`Album`/`ExternalResult`/`DownloadRequest`/etc.) crossing all seams.
- `internal/events/bus.go` — in-process EventBus backing `internal/api/stream.go` (WebSocket) and download progress; primary live channel to the frontend.
- `internal/matching` — matches search results against library (ISRC/metadata) to mark owned.
- `internal/resolver` — resolves adapter/track identity; constructed against `ServiceReloader.MatcherProvider()` so it reads the live matcher per-resolve.
- `internal/sync` — CRDT sync (HLC vector, per-field LWW, device pairing codes, Bearer token auth, Ed25519-signed changes, file manifests). Entity types and field names are the wire format and live in `sync.go`. `SyncQuerier` declares all persistence operations at compile time; pairing retains its separate interface. SQLite transaction selection and aggregate-value conversion remain in storage, with no mock-only changelog fallback. The change log only replicates facts; `internal/materialize` projects accepted changes onto the tables the app reads, installed via `SyncStore.SetMaterializer` in the composition root. It runs after the log commits and writes through the domain services without appending changes, so applying a peer's change cannot echo back. A change whose `value_json` does not parse is refused at the boundary rather than stored: the log is read back as JSON, so one unparseable row would fail the deferred-play recovery query for every catalog identity, not just its own. Unprojected plays remain retryable from the log: catalog adoption retries dependent plays, skipping any malformed row an older build stored, and startup retries missing history. Startup recovery (`RecoverUnusableChanges`) quarantines rows that cannot be used in `sync_quarantine`: an invalid signed remote copy, whose author vector is atomically reset so an authentic copy can be fetched again, and a play record whose value does not parse, which has no authentic copy to ask for and is only dropped, its own device included. It never re-signs remote changes. A malformed play also leaves the pending-projection queue when projection meets it, so draining does not wait on that startup pass.

  What replicates: catalog entities, per-track metadata (renames -> `track_override`, crops -> `track_crop`, quality -> `track_quality_override`, measured loudness -> `track_loudness`, uploaded art -> `entity_cover`), album and artist renames plus album art (`album`/`artist` entities -> `entity_override`, `entity_cover`), managed playlists, play history -> `plays`, recommendation additions -> `recommendation_add`, and Not interested marks -> `not_interested`.

  Album and artist changes cannot be keyed on a catalog id — there is no catalog entity behind them — so they travel under a **stable key** derived from the library's own names (`override.AlbumKey`, `override.ArtistKey`): the normalised primary artist plus title. A peer's change binds to whatever backend id this device has for that key, or waits under the key itself until one exists. Keys must always be derived from the library's original names, never from names an override has already rewritten, or the second rename of a thing keys differently from the first.

  A cover replicates as an address, not an image: the log carries `<sha256>.<ext>` and `p2p.Puller` fetches the bytes over `/reverb/cover/1.0.0` for any `entity_cover` row whose blob is missing. Until the bytes arrive the library backend's own art shows, so a missing blob is a delay, not a broken page.

  Everything per-track is keyed on the **catalog id**, never the backend track id, which is local to one library backend. Catalog ids are minted from a random token, so two devices mint different ids for the same track: `catalogEntity` changes replicate the entity itself, and `catalog.Adopt` fuses a peer's entity with a local one via the ordinary alias-collision merge. The peer's id keeps resolving afterwards through its `catalog` self-alias (`catalog.Resolve`), which merges repoint. Catalog entities are applied ahead of the rest of a batch, since everything else names a track by an id that means nothing until the entity has landed. Startup enumerates the active library through `syncemit.PublishLibrary`, so even a track with no play or playlist reference reaches a phone as metadata; the pass is idempotent and runs in the background.

- `internal/metadata` — local track rename and crop commands own persistence and best-effort sync emission. Their `BackendID` input is resolved to a catalog ID before publication. Peer projection calls the underlying non-emitting override/crop operations; it never calls local commands. These edits retain their existing notification behavior (no new events are introduced).
- `internal/syncemit` — the one place that knows how to write to the log: device identity, catalog-entity publication (`EnsureCatalogEntity`), plays, recommendation additions, per-track fields, plus the one-time `BackfillHistory` publish of state that predates replication.
- `internal/playlistcrdt` — managed playlists in both directions. Each track membership is its own field (`track:<digest>`) so concurrent additions on two devices both survive, and position is a fractional order key (`internal/fracidx`) so moving one track rewrites one key instead of renumbering the list. `Publish` diffs the playlist against the log rather than taking instructions, so every `playlistsync` mutator replicates through one call. Only `mode="once"` playlists replicate their tracklist; a `mode="synced"` mirror rebuilds itself from upstream on each device, so only its identity and settings travel.

  The member digest hashes `(source, externalID)` for search-source tracks, but a **library track's id belongs to one backend**, so those are keyed on `matching.Fingerprint` instead — otherwise the same recording added on two devices merges into two entries. `ExternalResult.CanonicalID` is stripped before publishing and re-applied from the local row on the way back in: it is device-local addressing, and carrying it would rewrite every member on every edit. A playlist row is only created once the log carries its `source`, since a peer sends its log in pages and half an entity must not fix the wrong identity onto a new row; fields the log does not carry are left as the row has them.
- `internal/cover` — user-uploaded album and track art. Blobs live under `<dataDir>/entity-covers`, addressed by the sha256 of their bytes, so one image applied to fifty albums is stored once. Nothing is written into the music library. An uploaded cover is surfaced by rewriting `CoverArtID` to `custom:<sha>.<ext>` on the way out of the API; `/cover/{id}` serves that from disk and everything else from the backend. `internal/api/decorate.go` is the single place library data passes through on its way out — renames, crops, and art are all applied there.
- `internal/recommend` — recommendation candidates for artist, track and playlist pages, Radio, Home shelves, and Mixes. It reads the live search sources, library and matcher per request. Deezer contributes related artists through `search.SimilarArtistsProvider`; Last.fm contributes similar recordings through `TrackSimilarity` and reuses the scrobbling API key; account-free ListenBrainz contributes both from its public datasets. A connected ListenBrainz account is also a `PersonalSource`: its collaborative-filtering recommendations join Discover Weekly as one more list (reason `personal`), and connecting or disconnecting regenerates that Mix. Candidate lists merge per request, keep source provenance, and are ranked by a small weighted model (`rank.go`): support from the seeds (a source's rank, summed across seeds), source agreement, the taste profile's affinity for the track and its artist, artist familiarity, and novelty. The taste profile (`taste.go`) is derived on each device from replicated qualified plays, playlist tracks, and Not interested marks, plus imported Last.fm history where Last.fm is linked. `internal/tastehistory` imports that history (top tracks and artists, and scrobbles from before the link) into the local, non-replicated `taste_history` table on linking and weekly after, subtracting scrobbles Reverb sent itself; it is taste input only, never plays, weighed per doubling of listens so Reverb's own plays soon outweigh it, and unlinking deletes it. Only the device holding the link has it; short recommendation skips are retained for quality stats but excluded from taste and ordinary listening stats, and never uploaded to a linked Last.fm or ListenBrainz account, since a scrobble claims a listen. Inputs are kept as exact integer sums per day and decayed with a 90-day half-life measured from the newest input's day, so devices holding the same data rank identically whatever order they stored it in; plays are folded in incrementally by rowid and rebuilt when one is removed, which shows up either as the qualified-play count falling or as a different play holding the fold's cursor, since SQLite hands a removed play's rowid to the next one recorded. Every result carries a reason ("Because you played X", "Fans of Y also like"). `internal/tastesettings` replicates Adventurousness and the Online recommendations switch on entity `tasteSettings`; with the switch off, unreadable settings, or failed online sources, Radio and similarity fall back to locally playable library tracks ranked from shared artist/album, managed-playlist co-occurrence, and playback-session co-occurrence. No external stream is resolved in that path. MusicBrainz IDs identify recordings and artists when present, with normalised artist/title or artist-name matching as the fallback. Track candidates are matched to something playable: the library copy (reported with its catalog id) or a search result whose recording identity matches, which keeps live cuts and same-titled songs by others out. One source failure does not discard successful peers; source collection and playable matching have separate deadlines. ListenBrainz spaces all of its requests, while track-similarity sources also back off after errors. Radio (`POST /recommendations/radio`) ranks similar tracks for several seeds together, then balances new against known (owned or played) music at the surface's share — half new — shifted by Adventurousness, where 0 and 100 exclude the other kind entirely; an artist seed first becomes a few of that artist's own tracks. Every surface declares a policy: all drop other versions (live, cover, remix, karaoke, instrumental, detected from title qualifiers) unless a seed is one, and collapse duplicate recordings on a fingerprint of primary artist plus title with reissue qualifiers removed; a discovery policy also drops owned tracks and anything played in the last 30 days. Radio, similar tracks and playlist suggestions are not discovery surfaces; Home shelves and Discover Weekly are. Home's "For you" shelves (`shelves.go`) are seeded from the most played tracks of the last 30 days and the most played artists of the last 90 ("Because you played X", "Artists you might like", "More from artists you love"), or from the artists the library holds most of before anything is played. A Mix (`mix.go`, ADR 0002) is a regenerated list, never a playlist: Discover Weekly refreshes Monday and Release Radar Friday, both at local midnight. Each draws its seeds only from inputs dated before its period began and orders the seed pool by a hash of a per-period seed, so devices holding the same plays make the same draw (ADR 0001). Library contents come from each device's own, unreplicated library bindings, so a draw seeded from the library (before anything is played) and Tracked artists qualified by library size can differ between devices. With online recommendations off or lookups failing, the last Mix stays with an offline note. Discover Weekly keeps tracks neither owned nor ever played, at most two per artist. Release Radar (`radar.go`) derives Tracked artists on every refresh (three qualified plays in 90 days, or five library tracks; Not interested artists never qualify), reads each `search.DiscographyProvider` for releases dated to the day within the last 14 days, deduplicates them across sources, and takes a few tracks from each. Shelves and Mixes are stored in the local, non-replicated `settings` table, so Home renders them at once; a read that finds them stale starts a background refresh, and `RunSchedule` rechecks the wall clock every 15 minutes so a device asleep at a refresh time catches up on launch or wake. Saving a Mix copies it into an ordinary managed playlist. Playlist suggestions are seeded from tracks spread through a managed playlist, never repeat one of its tracks, and page through the ranked list on Refresh; mirrored playlists get none. The Radio session itself lives in the web player (`web/src/lib/radio.ts`), over the core's queue (`internal/player`): it keeps three tracks queued ahead, refills from the latest tracks as seeds, never repeats a recording or queues a third track in a row by one artist, prewarms upcoming external tracks, and ends when something else is played or the queue is cleared. Listening steers the session: a skip (moving on having actually played less than half of a track; seeks do not count as listening) pushes its artist and the tracks recommended from or alongside it down, finishing or repeating a track pulls them up, and two skips of one artist stop it for the session. Each change re-ranks the tracks Radio queued without moving the listener's own; a new session starts unsteered. Recommendation-origin plays and library/playlist additions replicate, and Stats computes per-surface skip, completion, and add rates over the selected range. Not interested marks are filtered on every read, including cached results. The last successful online result remains in the per-device memory cache after its normal TTL and is returned with its original timestamp and an offline marker if a refresh fails; results never enter the change log (ADR 0001). `cmd/recommend-quality` evaluates Radio and similar tracks against a hidden tail of play history, can capture ListenBrainz responses for a real database into a replayable fixture, and compares deterministic replay metrics with a checked-in baseline.
- `internal/notinterested` — the owner's Not interested marks. A mark is one LWW field (`notInterested` / `mark`) under a key every device derives alike: the name-derived artist key for artists, `matching.Fingerprint` of the catalog identity's original metadata for library tracks, and source + external id otherwise, so the same recording marked on two devices is one mark. Undo writes null rather than a tombstone, since delete-wins would stop a later re-mark from ever beating an earlier undo. The projection writes `not_interested` without emitting.
- Manual device sync coalesces with an active exchange and retains pending, running, completed, no-device, or failed status through `/sync/status`. The UI polls this snapshot, so missed WebSocket events cannot hide completion or device failures. Exchange completion covers the change-log transfer; local projection and file downloads continue independently. Applied incoming batches publish `library.updated` after projection so open playlists and library views refresh.

- `internal/p2p` — libp2p host (fixed listen port, `--p2p-port`; `HostOptions.NoDiscovery` starts it without mDNS or the DHT), peer trust (`p2p_peer`), manifest/file sync handlers, cover-blob transfer, pull replication. A new pairing code also comes as a versioned pairing link for a QR code (`p2p.EncodePairPayload`: `reverb://pair?v=1` with the code, its expiry, the peer ID once and each dialable address without it), drawn as an SVG by `POST /pairing/code`; `POST /p2p/pair/redeem-qr` refuses a malformed, unknown-version or expired link before dialling, then seeds every address and pairs through the same challenge-response (`RedeemViaAddrs`), remembering all of them. Peers are dialed by stored multiaddr as well as by discovery, since mDNS multicast does not cross a VPN and the DHT runs in client mode; pairing accepts a full `/ip4/…/p2p/<id>` multiaddr and persists it on `p2p_peer.addrs`, or, given only the code, tries each connected peer that advertises the pairing protocol (`RedeemViaDiscoveredPeers`) — on a LAN mDNS has already connected every Reverb device, so the code alone suffices there. A connection is up before libp2p's identify exchange reports what the other end speaks, so a redeem that finds no candidate waits — briefly, and only while some connected peer is still unidentified — rather than telling the owner their other device does not exist; a network where every peer is identified and none is a Reverb device still fails at once. The exchange is a mutual challenge-response (`/reverb/pair/2.0.0`, `internal/p2p/pairproof.go`): the code never crosses the wire, and neither side is trusted, nor does a session token change hands, until it proves possession with an HMAC under a stretched key derived from a live code and both nonces. A peer that cannot prove possession — including one speaking the pre-proof protocol, which offered the plaintext code and accepted a bare success — is refused. A redeeming peer sends the device ID it already authors changes under and is bound to that (`PairingService.RedeemAs`), since the sync handler takes identity from the connection. A legacy pairing alias is repaired only when both existing device rows are already pinned to that connection's public key and no other paired peer owns the requested ID; request announcements cannot authorize the repair. Other mismatches are refused.

  File names are a household concern, not a per-device one: a name is minted once, on whichever device runs the download, and then travels to peers that may be any platform. `internal/portablename` therefore sanitises unconditionally rather than for the running platform, to the narrowest of the three rule sets — Windows's illegal characters, its refusal of a trailing dot or space, and the DOS device names. Both download adapters apply it: yt-dlp takes sanitised literals in its `-o` template, giving the stem a `(2)` suffix rather than minting over a track already on disk, and since spotDL and yt-dlp's `%(title)s` fallback substitute their own names from source metadata, both adapters also sweep what they just wrote (`download.BeginPortableSweep`, which snapshots the output directory first so the sweep touches only this download's file). `portablename.LocallyStorable` is the deliberately platform-dependent counterpart, asking whether *this* device can write a name a peer already minted.

  A file that cannot be fetched backs off instead of being retried every round (`internal/p2p/fetchfailure.go`, `file_fetch_failure`). The round is capped, so a permanently failing entry does not merely waste its own attempt — it holds a slot a fetchable file needed. Backoff doubles from five minutes to a day, is keyed on the peer as well as the content — a round runs per peer, and a device that no longer holds a file says nothing about one that does — and resets when a peer advertises the file at a new path, which is exactly what a migration on that device produces. An unwritable remote path is recognised when the round's candidates are chosen rather than discovered as a failed write. `GET /p2p/file-failures` surfaces all of it, per peer, because a file silently absent forever is indistinguishable from one still in flight.

  `internal/portablemigrate` renames an established library onto those same portable names, which is what lets a Windows device pair with a library built on Linux or macOS. It is an owner-initiated action (`POST /p2p/portable-names`), not a startup task, since it touches the owner's own music folder. The offer is driven by `GET /p2p/portable-names`, which counts this device's own unportable names: the device holding them is not the one that notices, since a Linux or macOS device stores them without complaint while the Windows peer that cannot copy them has nothing to rename. Entries move deepest-first so a directory's contents are relocated while it still has the name they were found under; each move is one atomic rename with nothing journalled beforehand, so an interrupted run leaves every file at its old or its new name and rerunning finishes the job; a target name already in use is given a free one rather than overwritten. The migration carries each `file_manifest` row across itself, preserving the content hash so peers already holding the bytes do not transfer them again, then re-indexes the library and bumps the binding epoch so the resolver re-resolves each track's backend id. A run killed between the renames and the manifest update is repaired on the next run from what is on disk rather than from a record of what the last one did, since no such record survives a crash. Listening history, playlists and ratings are keyed on catalog ids, which a rename does not touch.
- `internal/player` — the play queue, owned by the core so every player plays one implementation of it (ADR 0003). One queue per player session (`/player/{session}`; a desktop window, a browser tab, the phone), at most 32 kept, least recently used dropped. Entries carry an id and an origin (`listener` or `radio`); a listener's enqueue goes ahead of the first upcoming Radio entry. The queue owns next/previous, repeat, shuffle order (led by the current entry; a jump moves the picked entry up rather than dropping what lies between), up next, and what an end means; `playId` changes whenever the current entry must start from its beginning, and `ended`/`next` carry the entry they were sent for so a stale one changes nothing. Each change is answered with the whole queue; a `player.queue` WebSocket notice carries only the session and revision, since a queue can hold thousands of tracks. When a Radio session stops by itself, `radio-ended` makes the tracks it lined up the listener's, so later queueing goes after them as it would with no Radio. The player keeps playback: loading, seeking, crop, recovery, restarting a track more than three seconds in on "previous", and deciding a dead track is skipped.
- `internal/pyrun` — runs Python tools as modules (`Runner.RunModule`) instead of bundled executables; `Host` uses an installed interpreter, and `Module` adapts a runner to the executable-shaped runner the yt-dlp and spotDL adapters and `extstream` take.
- `internal/store` — SQLite (`modernc.org/sqlite`), migrations `internal/store/migrations/*.sql` (goose), sqlc `internal/store/queries` -> `internal/store/db` (`make gen`).
- `internal/api` — chi handlers, OpenAPI at `/api/v1/openapi.yaml`, `embed.go` embeds SPA. Download transport records and frontend event validation are generated from OpenAPI; see [contracts.md](contracts.md).
- `internal/auth` + `internal/api/roles.go` — a single household owner (`local`, holding every capability) is the intended end state, not a stopgap. There are no accounts, no login and no sessions: the HTTP API is loopback-only (Reverb refuses a non-loopback bind without `--allow-network-access`) and the transport is the access boundary, so `requireAuth` fabricating the owner for every request is correct. Paired devices authenticate separately — Bearer tokens on `/sync`, libp2p peer identity on P2P. The capability gates (`can_manage_library`, etc.) are therefore never denials in practice; they document intent. Per-user columns from migration 0013 are inert by design.

  `csrfGuard` (`internal/api/security.go`) stays: with no session cookie it is tempting to think CSRF is impossible, but reaching the loopback port *is* the ambient credential, so a page in the user's browser could otherwise POST to Reverb as the owner. `hostGuard` sits beside it because the Origin check alone cannot see a DNS-rebinding page, which controls `Origin` and `Host` together and makes them agree; it rejects any request — read or write — whose `Host` is neither loopback nor in `Deps.AllowedHosts`, since a rebound page is same-origin to the browser and reads the responses it gets back. In the desktop build the window's own origin counts as local too: the SPA there is served by the same handler through the Wails asset server, so its requests arrive with `Host: wails` (`wails.localhost` on Windows) and a fabricated TEST-NET peer address rather than anything loopback — the same two hosts `ws.go` accepts as WebSocket origins, and the same reason `authenticateSync` treats them as local. Both guards exempt `POST /api/v1/sync` once its Bearer token has authenticated a paired device — no page can forge that shape without CORS — and nothing else.

### Frontend (`web/`)

React 19 + TypeScript, Vite, TanStack Query, Zustand, Tailwind, react-router.
- `web/src/routes/` — one file per page (Home, Library, Search, Album, Artist, Downloads, Requests, Settings, Admin, Stats, …) with co-located `*.test.tsx`.
- `web/src/lib/` — thin `*Api.ts` fetch wrappers, Zustand `*Store.ts` (player, download, coverage, auth, library revision, everywhere/search, now-playing, pending-play), `audioEngine.ts` (a thin player: it plays the core queue's current entry, applied with `apply`, and reports ends and skips back; `playerStore.ts` sends the listener's queue actions to `/player/{session}` one at a time and applies each answer), `mediaSession.ts`, `playTracker.ts`, `realtime.ts` (WebSocket), `paletteService.ts`/`paletteWorker.ts`.
- `web/src/components/` — shared UI.
- Dev: Go proxies Vite (`--dev`); prod: SPA embedded into binary (`-tags prod`).

### Desktop (`desktop/`)

Wails wrapper — same monolith on `127.0.0.1:0` (`desktop/main.go:boot`, `desktop/app.go:App`). Listens on random port, publishes `LocalAPIPort` so the AssetServer-served SPA dials the real API (WS cannot upgrade through Wails). DB at `~/Library/Application Support/Reverb/reverb.db` (macOS) / `~/.config/reverb/reverb.db` (Linux XDG) / `%AppData%\reverb\reverb.db` (Windows) with legacy `./data/reverb.db` migration; downloads in `~/Music/Reverb`, `%USERPROFILE%\Music\Reverb` on Windows (`internal/desktop/paths.go`). Bundled `ffmpeg`/`navidrome`/`spotdl`/`yt-dlp`/`deno` resolved via `desktop/bundle.go:ResolveBundledTools` and injected before `config.Load` (`ApplyBundledToolEnv`); fetched into `desktop/tools/` via `make desktop-deps`. Install bundles (and the Windows tool set) carry a relocatable Python runtime with spotDL/yt-dlp launchers (`desktop/tools/build-python-runtime.sh` on macOS/Linux); startup publishes that interpreter as `REVERB_YTDLP_PYTHON`, and the daily yt-dlp upgrade runs only there, never against a system Python. Build tags `desktop,production,webkit2_41` (`desktop/frontend.go` vs `desktop/run_fallback.go` plain HTTP). Single-instance lock in `desktop/singleinstance.go`.

Desktop close behaviour hands the backend to a headless `--background` process
after releasing the single-instance lock. It runs the same composition root at
reduced CPU priority, without Wails or a webview. Reopening requests shutdown via
a user-private Unix socket and waits for resource release before booting the UI.
The local `desktop.json` preference controls this handoff; an explicit quit or
update restart bypasses it. No login service is installed. See
[desktop background sync](../desktop/README.md#background-sync).

Everything about the desktop app that depends on the host's process model lives
behind a per-OS seam, so a port changes implementations rather than editing
shared logic. `internal/childproc` is the shared one — console suppression,
detaching a child that must outlive its parent, low-priority spawning, the
terminate-then-kill shutdown escalation, and the pid liveness and identity
checks that stop a stale pid file from signalling an unrelated process. The
rest are local to the package that owns them: the single-instance lock
(`desktop/singleinstance_unix.go`), the background control channel
(`desktop/background_channel_unix.go`), bundled-tool file naming and
executability (`desktop/bundle_unix.go`), and the updater's backup location,
post-install resealing and relaunch command (`desktop/updater/platform_*.go`).
Each seam's doc comment states the guarantee callers rely on, not the unix
mechanism that currently provides it.

### Configuration

Flags > env > defaults. Flags: `--port`/`--bind`/`--p2p-port`/`--db`/`--dev`/`--update-repo`. Env: `REVERB_PORT`/`REVERB_BIND`/`REVERB_P2P_PORT`/`REVERB_DB`/`REVERB_DEV`/`REVERB_DOWNLOAD_DIR` / `REVERB_SPOTIFY_CLIENT_ID/SECRET` / `REVERB_LIBRARY_PASSWORD` / `REVERB_SPOTDL_PATH`/`REVERB_NAVIDROME_BIN`/`REVERB_YTDLP_PATH`/`REVERB_DENO_PATH` (+ navidrome listen/port vars) / `REVERB_PYTHON` (phone profile on Linux) — see `README.md` + `internal/config`. Secrets via env/`.env` only (gitignored; `.env.example` template).
