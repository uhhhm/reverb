# Ticket 09 verification

Baseline: `e2b938dd9284547a41669bc0a973cc8a25f0ac66` on `main`.

## Failure cases and test boundaries

Before implementation:

- A successful track or artist mark refreshes only similarity queries, leaving Home, Mixes and playlist suggestions current in the client cache.
- Undo and either recommendation setting have the same incomplete refresh policy.
- An active view must fetch again immediately; an inactive cached Mix or suggestion page must fetch when reopened, including other kinds, playlists and pages.
- A failed mutation must retain prior answers and marks/settings, with the existing error feedback.
- Broad invalidation could refresh unrelated library/download data or accidentally invoke Radio, queue changes, Mix generation or playlist creation.
- Moving query identities could change enabled conditions, stale times or background polling.

The ticket specifies the seams: real frontend query/mutation hooks with controlled HTTP responses, and the rendered SPA with intercepted HTTP. The hook regression owns cache lifecycle, including active and inactive variants and unrelated caches. Existing tests mock recommendation hooks and cannot detect this omission. The browser scenario owns UI actions, routing and visible results. Neither needs a test-only production export.

## Regression evidence

The hook tests were written before production changes. The final fixture was
also rerun against the baseline production files: all five successful actions
failed because shelves, the Mix list, the active Mix and playlist suggestions
retained `Before`, while both similarity views changed to `After`. The five
failed-mutation cases passed. All ten cases pass with the shared query policy.

The browser fixture intercepts HTTP and WebSocket traffic around the production
SPA. It serves three named library tracks and two artists, two Mix kinds, Home
shelves, an empty managed playlist with suggestions, and similar tracks/artists.
Responses depend on accepted marks and settings; one mark receives HTTP 500.
This isolates client invalidation from recommendation ranking. Navigation uses
browser history within one document; the scenario asserts exactly one document
request. It checks visible changes, fresh recommendation requests, the marks
list, failed-mark feedback, and absence of Radio/queue/playlist-save mutations.
